# 安全与授权边界

## 1. 结论

客户部署包不应依赖“加密压缩包”防破解。程序必须在客户机器上解密并运行；拥有 root 权限的人可以读取解密后的文件、进程内存，或直接修改授权判断。加密和混淆最多增加分析成本，不能作为授权边界。

生产交付使用三层防线：

1. HTTPS 保护下载链路。
2. 发布私钥对版本包做独立签名，安装器内固定公钥并在解压前验证。
3. 授权由平台服务端签发、轮换和吊销；客户机只持短期凭据或平台私钥签名的离线许可证。

## 2. 威胁模型

| 场景 | 当前防线 | 明确边界 |
|---|---|---|
| 下载被替换 | 安装器 SHA-256、版本包 RSA/SHA-256 签名 | 发布私钥泄露后必须立即换钥并停用旧公钥 |
| 普通账号读取配置 | `0600` 环境文件、独立 AES-GCM 主密钥 | root 仍能读取进程环境和内存 |
| Web 登录爆破 | 每 IP 失败限速、常量时间比较、12 小时会话 | 正式公网入口仍应在反向代理增加 IP/地域/并发限制 |
| 第三方前端脚本劫持 | Lucide 固定版本随包发布，CSP 只允许同源脚本 | 更新依赖时必须重新构建并签名 |
| SDK 跨租户伪造 | 凭据只存摘要，租户和区服从认证上下文注入 | 客户 root 可窃取本机凭据，因此服务端必须支持轮换和吊销 |
| 客户复制或修改二进制 | 在线授权、短期租约、服务端功能开关 | 完全离线且客户拥有 root 时无法做到不可绕过 |

## 3. 发布签名

发布私钥只保存在发布机或 CI 密钥库，不进入源码、安装器、版本包、客户服务器或备份。

首次生成 3072-bit RSA 发布密钥：

```bash
umask 077
openssl genrsa -out /secure/ponytail-release-rsa.pem 3072
```

生产构建：

```bash
PGR_NODE_BIN=/opt/node-v22.23.1-glibc217/bin/node \
PGR_NODE_SHA256=088f98ed4506ee8dc2525706a0b809304c4753a26a24a785ea161fdecc85d76f \
PGR_RELEASE_SIGNING_KEY=/secure/ponytail-release-rsa.pem \
  bash deploy/build-linux-bundle.sh \
  --base-url https://download.example.com/releases
```

构建使用 `Cargo.lock` 的锁定依赖，并校验被打包 Node 运行时的 SHA-256。输出包含版本包、`.sig`、公钥、安装器以及两个 SHA-256 文件。客户命令先校验安装器，再由安装器内固定的公钥校验版本包哈希和独立签名。`--unsigned-lab` / `--allow-unsigned-lab` 只允许封闭实验环境使用。

## 4. 授权设计

最终授权应在 Go 多租户控制平面实现：

- 每张客户密钥映射固定 `tenant_id`、套餐、到期时间和区服数量。
- 客户 Agent 使用设备注册凭据换取 15 到 60 分钟短期租约。
- 租约包含 `tenant_id`、`server_id`、功能权限、过期时间、随机序号和平台签名。
- Agent 缓存有限宽限期；超过宽限期停止云端分析和新事件接收，但不破坏客户游戏进程。
- 平台支持单区服吊销、密钥轮换、并发实例限制和审计记录。
- 永久封号、扣除资产等权威动作仍由客户游戏插件执行并回传幂等回执。

离线客户可以使用平台私钥签名、带到期时间和服务器指纹的许可证，但这只能防止普通复制，不能抵抗客户 root 修改二进制。核心模型、跨客户图谱和授权私钥应保留在平台端。

## 5. 生产上线检查

- Portal 默认绑定 `127.0.0.1`，前置可信 HTTPS 反向代理。
- 设置 `RISK_BEHIND_TLS_PROXY=1` 和精确的 `RISK_TRUSTED_PROXY_IPS`。
- 防火墙不直接开放 Agent 端口；Agent 只监听 loopback。
- 数据库账号仅授予所需业务库 `SELECT`。
- 每个客户实例使用独立 Linux 服务账号、独立数据目录和独立主密钥。
- 定期轮换 Portal 卡密、SDK 凭据、数据库只读密码和 AI API Key。
- 备份只包含密文配置和行为数据；主密钥单独保管。
- 发布前运行 `node self_check.mjs` 和安装器 `--check-only`。
